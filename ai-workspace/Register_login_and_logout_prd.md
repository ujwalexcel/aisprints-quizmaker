# Register, Login, and Logout - Technical PRD

## Overview/Problem

Teachers need a shared quiz maker where multiple collaborators can build a test bank of multiple-choice questions. Before any question content can be created, the application must know who is using it.

**Implemented (August 2026):** Teacher registration, login, logout, session cookies, D1-backed user storage, HTTP auth API routes, and shadcn/ui auth pages. Successful authentication lands on a protected `/mcqs` stub. All four implementation phases are complete; automated tests (44) and manual browser verification pass.

---

## Hypothesis

We believe that providing secure teacher registration and session-based login will enable multiple educators to collaborate on a shared quiz platform without building question content in phase one.

---

## Scope

### In Scope

What will be built in this feature:

- Cloudflare D1 database with a `users` table and an initial migration
- Password hashing at registration and verification at login (server-side; never store plain-text passwords)
- `UserService` in `src/lib/services/` with create, read, update, and delete operations
- HTTP POST API route handlers for register, login, and logout
- Register page (`/register`), login page (`/login`), and authenticated MCQs stub page (`/mcqs`)
- Redirect to `/mcqs` after successful register or login
- Redirect to `/login` after logout
- Basic form validation (required fields, email format, password minimum length, unique username/email)
- Session management so login state persists across requests and logout clears it
- Route protection on `/mcqs` so unauthenticated users are sent to `/login`
- **Test-driven development with Vitest** — each phase starts by writing failing unit tests, then implements code until tests pass

### Out of Scope

What is explicitly not being built now but may be considered later:

- MCQ creation, editing, listing, or collaboration features
- Password reset or email verification
- OAuth / social login (Google, Microsoft, etc.)
- Role-based access control (admin vs teacher)
- User profile editing UI (service methods exist; no profile page yet)
- Remember-me / long-lived sessions beyond a standard session cookie
- Rate limiting and CAPTCHA on auth endpoints
- End-to-end browser automation (Playwright/Cypress) — unit and integration tests via Vitest only in this phase
- Real D1 or Workers runtime inside the test suite (`@cloudflare/vitest-pool-workers`) — D1 is mocked at module boundaries per project testing conventions

### Cut

Things that were considered during planning but deliberately removed (and why):

- **Client-side password hashing before POST** — Hashing on the client does not improve security when HTTPS is used; it turns the hash into the effective credential. Passwords are sent over HTTPS in POST bodies; hashing and comparison happen on the server only.
- **JWT in localStorage** — Session cookies (HTTP-only, Secure in production) are simpler and safer for a first-party web app on Workers.
- **Server Actions instead of API routes** — Server Actions are the default pattern in this repo, but explicit HTTP endpoints were requested for register, login, and logout. Route handlers in `src/app/api/` will be used for this phase.

## Technical Requirements

### Database Schema

One table is required for phase one. Session state is handled via signed cookies (no `sessions` table in this phase).

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
  first_name TEXT NOT NULL,
  last_name TEXT NOT NULL,
  username TEXT NOT NULL UNIQUE,
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_email ON users (email);
CREATE INDEX idx_users_username ON users (username);
```

| Column | Type | Notes |
|--------|------|-------|
| `id` | TEXT PK | Opaque identifier; generated by D1 default |
| `first_name` | TEXT | Required |
| `last_name` | TEXT | Required |
| `username` | TEXT | Required; unique; used for display and login lookup |
| `email` | TEXT | Required; unique; used for login lookup |
| `password_hash` | TEXT | bcrypt (or equivalent) output; never plain text |
| `created_at` | DATETIME | Set on insert |
| `updated_at` | DATETIME | Set on insert and update |

**Migration setup (one-time project steps):**

1. `npx wrangler d1 create aisprints-quizmaker-db`
2. Add `d1_databases` binding named `DB` to `wrangler.jsonc`
3. `npm run cf-typegen`
4. `npx wrangler d1 migrations create aisprints-quizmaker-db create_users_table`
5. Place the SQL above in the generated migration file
6. Apply locally only: `npx wrangler d1 migrations apply aisprints-quizmaker-db --local`

### API Endpoints

All auth endpoints live under `src/app/api/auth/`. Request bodies are JSON. Passwords travel over HTTPS in the POST body; the server hashes on register and verifies on login.

#### POST /api/auth/register

Creates a new user and starts a session.

**Request Body:**

```json
{
  "firstName": "Jane",
  "lastName": "Doe",
  "username": "jdoe",
  "email": "jane.doe@school.edu",
  "password": "securePassword123"
}
```

**Response:**

- Success (201): `{ "user": { "id", "firstName", "lastName", "username", "email" }, "redirectTo": "/mcqs" }` plus `Set-Cookie` session header
- Error (400): Validation error — missing fields, invalid email, password too short, username/email already taken
- Error (500): Server or database error

**Server behavior:**

1. Validate input with Zod
2. Reject if username or email already exists
3. Hash `password` with bcrypt (cost factor 10–12)
4. Insert row via `UserService.createUser`
5. Create session cookie
6. Return user object (no password hash) and redirect hint

#### POST /api/auth/login

Authenticates an existing user by email or username plus password.

**Request Body:**

```json
{
  "identifier": "jane.doe@school.edu",
  "password": "securePassword123"
}
```

`identifier` accepts either email or username.

**Response:**

- Success (200): `{ "user": { "id", "firstName", "lastName", "username", "email" }, "redirectTo": "/mcqs" }` plus `Set-Cookie` session header
- Error (401): Invalid credentials (generic message: "Invalid email/username or password")
- Error (400): Validation error
- Error (500): Server error

**Server behavior:**

1. Validate input
2. Look up user by email or username via `UserService`
3. Compare submitted password to stored hash (bcrypt compare)
4. On match, set session cookie and return user
5. On mismatch, return 401 without revealing whether the account exists

#### POST /api/auth/logout

Ends the current session.

**Request Body:** none (session read from cookie)

**Response:**

- Success (200): `{ "redirectTo": "/login" }` plus cookie cleared via `Set-Cookie` (Max-Age=0)
- Error (401): No active session (optional — may still return 200 and clear cookie)

### User Service

Location: `src/lib/services/user-service.ts`

The service centralizes all D1 access for users. Route handlers and (future) Server Actions call this module; they do not query D1 directly.

| Method | Purpose |
|--------|---------|
| `createUser(data)` | Insert user; hash password before persist |
| `getUserById(id)` | Fetch by primary key |
| `getUserByEmail(email)` | Fetch by email (login) |
| `getUserByUsername(username)` | Fetch by username (login) |
| `getUserByEmailOrUsername(identifier)` | Single lookup for login |
| `updateUser(id, data)` | Update allowed fields; re-hash password if provided |
| `deleteUser(id)` | Remove user row |
| `verifyPassword(plain, hash)` | Compare password to stored hash |

Return type for reads should omit `password_hash` in the public user shape exposed to API responses.

### Session Management

- Use an HTTP-only cookie (e.g. `session`) containing a signed payload with `userId` and expiry
- Sign with `SESSION_SECRET` from environment (`.dev.vars` locally, `wrangler secret put` in production)
- Cookie flags: `HttpOnly`, `SameSite=Lax`, `Secure` in production, `Path=/`
- Helper module: `src/lib/auth/session.ts` — create, read, destroy session
- Route guard on `/mcqs` via server page + `getMcqsRedirectPath` (no `middleware.ts`)

### User Interface Requirements

#### Landing / Home (`/`)

- If authenticated, redirect to `/mcqs`
- If not authenticated, redirect to `/login` (sign up available from the login page)

#### Register Page (`/register`)

- Form fields: First Name, Last Name, Username, Email, Password, Confirm Password
- Client-side validation for immediate feedback; server validates again
- Validation rules:
  - All fields required
  - Email: valid format
  - Username: 3–32 chars, alphanumeric and underscore only
  - Password: minimum 8 characters
  - Confirm password must match password
- Submit: POST to `/api/auth/register`; on success navigate to `/mcqs`
- Link to login page for existing users
- Display server error messages (duplicate email/username, generic failures)

#### Login Page (`/login`)

- Form fields: Email or Username, Password
- Submit: POST to `/api/auth/login`; on success navigate to `/mcqs`
- Link to register page
- Display generic invalid-credentials message on 401

#### MCQs Stub Page (`/mcqs`)

- Protected route — requires valid session
- Placeholder content, e.g. "MCQ Test Bank — coming soon"
- Show logged-in user's name or username
- **Logout** button: POST to `/api/auth/logout`; on success navigate to `/login`

#### Shared UI

- Built from **shadcn/ui blocks** (Base UI, `base-nova` style) with **Tailwind CSS v4** theme tokens
- Auth page shell: centered layout (`min-h-svh`, `max-w-sm`, responsive padding) wrapping each form
- Components: `src/components/login-form.tsx` (`LoginForm`) and `src/components/signup-form.tsx` (`SignupForm`)
- shadcn primitives: `Card`, `Field`, `FieldLabel`, `FieldDescription`, `FieldError`, `Input`, `Button`
- Cross-links use Next.js `Link` (`/login` ↔ `/register`)
- **Omitted from shadcn block template** (out of scope): “Login with Google”, “Sign up with Google”, “Forgot your password?”
- **Adapted from block template** (PRD requirements):
  - Signup uses first name + last name + username (block template had single “Full Name” only)
  - Login accepts email **or** username (block template had email-only label; description updated accordingly)
- MCQs page uses `Card` + `LogoutButton` (`src/components/auth/logout-button.tsx`)
- Accessible form labels, `FieldError` for validation and server errors

## Test-Driven Development Approach

This feature is built **test-first** with **Vitest**. Each implementation phase follows the same rhythm:

```
RED → GREEN → REFACTOR → VERIFY
```

| Step | Action |
|------|--------|
| **RED** | Write the phase's Vitest tests first. Run `npm test` — new tests must fail because production code does not exist yet. |
| **GREEN** | Implement the minimum code to make those tests pass. |
| **REFACTOR** | Clean up while keeping tests green. |
| **VERIFY** | Confirm phase acceptance criteria **and** `npm test` all pass before starting the next phase. |

### Vitest setup (once, at start of Phase 1)

Vitest is not installed in the starter. Bootstrap it before writing phase tests:

```bash
npm install -D vitest @vitejs/plugin-react @testing-library/react @testing-library/user-event jsdom vite-tsconfig-paths
```

Add `vitest.config.ts` at the repo root and scripts in `package.json`:

```json
"test": "vitest run",
"test:watch": "vitest"
```

See `.cursor/skills/testing/SKILL.md` for full config, mocking patterns, and conventions.

### Testing conventions for this feature

- **Colocate tests**: `src/lib/services/user-service.ts` → `src/lib/services/user-service.test.ts`
- **Mock at boundaries**: Mock `getCloudflareContext()` and D1; never hit a real database in unit tests
- **Assert behavior, not internals**: Test return values, thrown errors, HTTP status codes, and user-visible UI — not private function calls
- **Cover failure paths**: Validation rejections, duplicate users, invalid credentials, missing session
- **No hollow tests**: Every test must be able to fail for a real reason

### Phase completion gate

A phase is **done** only when **both** are true:

1. All phase acceptance criteria checkboxes for that phase are satisfied
2. `npm test` exits 0 with all tests for that phase (and prior phases) passing

Manual smoke tests (`npm run preview`, browser) supplement but do not replace automated tests for API and service layers.

### Request flow

```
Register/Login form (client)
  → fetch POST /api/auth/*
    → Zod validation (auth.ts)
    → UserService (D1) + bcrypt
    → createSession (HMAC cookie)
  → router.push("/mcqs")

/mcqs (server)
  → cookies() → getSession()
  → getMcqsRedirectPath() → redirect("/login") if null
  → getUserById() → render stub + LogoutButton

Logout (client)
  → fetch POST /api/auth/logout
  → router.push("/login")
```

## Risks and Mitigation

### Technical Risks

- **Risk**: D1 bindings behave differently in `npm run dev` vs `npm run preview`
- **Mitigation**: Document and test auth flows with `npm run preview`; note limitation in README or AGENTS.md when D1 is added

- **Risk**: Weak or missing `SESSION_SECRET` allows session forgery
- **Mitigation**: Require secret in env; fail fast at startup if missing in preview/production paths

- **Risk**: SQL injection via user input
- **Mitigation**: Prepared statements with bound parameters only; no string concatenation in SQL

### User Experience Risks

- **Risk**: Teachers confuse username vs email at login
- **Mitigation**: Single "Email or username" field with clear label

- **Risk**: Unclear errors on duplicate registration
- **Mitigation**: Return specific messages for duplicate email vs duplicate username

## Troubleshooting Guide

### Auth routes return 500 or "DB is undefined"

**Problem:** Auth API fails during local dev on port 3000

**Cause:** D1 binding unavailable in Node dev server, or migration not applied, or missing `SESSION_SECRET`

**Solution:** Set `SESSION_SECRET` in `.dev.vars`; run `npx wrangler d1 migrations apply aisprints-quizmaker-db --local`; use `npm run preview` instead of `npm run dev`

### Root URL shows old Next.js starter page

**Problem:** `http://localhost:3000` shows default starter content

**Cause:** Stale dev server or uncommitted Phase 4 changes

**Solution:** Restart `npm run dev` after pulling latest; expected behavior is redirect to `/login` (`src/app/page.tsx`)

### D1 binding / placeholder errors

**Problem:** `Wrong number of bindings` in queries

**Cause:** Mixed `?` and `?1` placeholders

**Solution:** Use numbered placeholders only (`?1`, `?2`, …)

### Vitest `@/` import failures

**Problem:** Tests cannot resolve `@/lib/...`

**Solution:** Ensure `vite-tsconfig-paths` in `vitest.config.ts`

### Vitest `server-only` import failures

**Problem:** Tests fail resolving `server-only`

**Solution:** Alias in `vitest.config.ts` → `src/test/server-only-stub.ts`
